基础版本控制

以下操作均在测试仓库 test-dir/ 中进行：

1. 添加仓库

使用 git init 初始化仓库，此时文件夹 test-dir/ 已绑定到一个 Git Repo：

2. 将文件添加到版本库

  1. 使用 git add [filename] 将文件加入版本库
  2. 使用 git commit -m “describe” 将已添加的文件提交到仓库，提交描述为 “describe”
  • commit 相当于为仓库添加一个版本快照，并对快照进行管理

3. 查看仓库状态

使用 git status 查看仓库当前状态：

使用 git diff 查看已修改但未提交的内容：

4. 切换快照版本

使用 git log 查看从最近到最远的提交日志，使用 git reset --hard commit_id 回到指定版本的已提交状态：

  • –soft：回到上个版本的未提交状态
  • –mixed：回退到上个版本的已添加未提交状态
  • commit_id 可以是快照 id，也可以是 HEAD^（上个版本）、HEAD^^（向上第 2 个版本）、HEAD~N（向上第 N 个版本）；也支持填写部分 commit_id，由系统自动匹配
  • 使用 git reflog 查看从近到远的所有提交日志，可以找回过去的提交内容

提交信息规范

在团队协作或开源项目中，规范的 Git 提交信息能极大提升代码库的可读性与可追溯性，便于自动生成 CHANGELOG 和版本管理。目前最主流的规范是 Conventional Commits（基于 Angular 规范），格式如下：

1. 常用类型（type）

类型 说明
feat 新功能（feature）
fix 修复 bug
docs 文档变更
style 代码格式（不影响代码运行的变动，如空格、缩进等）
refactor 重构（既不是新功能也不是修复 bug）
perf 性能优化
test 增加或修改测试
chore 构建过程、辅助工具或依赖库的变动（如修改构建脚本、升级依赖）
revert 回滚某个提交

2. 作用域（scope）

  • 可选，表示本次修改影响的范围（如模块、文件名、组件名）
  • 例如：feat(allocator): add boundary tag coalesce
  • 若修改涉及多个模块，可以省略 (scope)

3. 主题（subject）

  • 必须使用祈使句（动词开头，如 add、fix、update），不使用过去式
  • 首字母小写，结尾不加句号
  • 长度尽量控制在 50 字符以内，简洁概括改动

4. 正文（body）

  • 可选，用于详细描述修改的原因、如何修改、影响范围等
  • 每行不超过 72 字符
  • 与主题之间空一行

5. 脚注（footer）

  • 可选，通常用于说明 Breaking Changes 或关联 Issue / PR
  • 格式：
    BREAKING CHANGE: <description>
    Closes #123, #456
