Podman-Quadlet

Podman

核心概念：无守护进程
Podman 没有后台守护进程，每个容器都是 fork 出的子进程

  • 不需要超级用户权限(sudo systemctl start docker)开箱即用
  • Rootless 运行，容器在用户UID下运行，无需root权限
  • 语法与docker基本兼容

与 Docker 的关键差异

Docker Podman

核心命令速记

Quadlet

核心定位：Podman 原生的 systemd 集成方案

  • Podman 项目第一方组件（podman RPM 包内置），零额外依赖
  • .container 文件 → systemd 单元，自动生成 service
  • 容器的生命周期交给 systemd 管理：开机自启、崩溃重启、日志走 journald
  • 对比 podman-compose：无守护进程，不需要额外安装，适合长期运行的生产服务

Quadlet 配置与使用方式

核心机制：systemd 生成器
Quadlet 本身不运行任何守护进程，它是挂载在 systemd 上的 generator。每次执行 systemctl --user daemon-reload 时，Podman 的 systemd 生成器扫描 ~/.config/containers/systemd/ 目录，将 .container / .volume / .network / .pod / .build 文件实时转换成对应的 service 单元。这意味着：

  • 文件→服务的转换是幂等的，改配置后只需 daemon-reload + restart
  • 生成的 service 文件在 /run/user/1000/systemd/generator/ 或 ~/.config/systemd/user/ 下，可以直接 cat 查看
  • 容器的整个生命周期由 systemd 接管，Quadlet 不参与运行时

文件类型与命名

Quadlet 根据文件后缀决定生成什么：

后缀 生成单元 用途
.container .service 最常用，定义单个容器
.volume .volume 命名卷（可跨容器共享）
.network .network 自定义网络
.pod .pod Pod（一组共享网络的容器）
.build .image 从 Containerfile 构建镜像

文件名中的 - 会被映射为 systemd 单元名中的 -，例如 astrbot-bot.container → astrbot-bot.service。

.container 文件标准结构

[Container] 段 —— 容器运行时参数，指令名与 podman run 参数一一对应：

指令 等价 CLI 说明
Image= podman run <image> 镜像地址，必填
ContainerName= --name 容器名，省略则用单元名
PublishPort= -p 端口映射，可多次出现
Volume= -v 卷或绑定挂载，可多次出现
Environment= -e 环境变量，可多次出现
Network= --network 指定网络
Enforce=always podman rm -f + podman run 每次启动强制重建容器（等价 --replace）
AutoUpdate=registry — 允许 podman auto-update 更新此容器
Pull=always --pull=always 每次启动前拉取最新镜像

[Service] 段 —— 映射到 systemd service 单元，控制服务行为：

指令 说明
Restart=on-failure 异常退出时自动重启
RestartSec=10 重启前的等待秒数
TimeoutStartSec=120 启动超时（秒），镜像较大的建议设长一些
Environment= 也可放这里，效果相同

Quadlet vs Podman Compose

Quadlet Podman Compose
定位 Podman 原生方案 Docker Compose 兼容层
工作方式 .container 文件 → systemd 单元 翻译 compose.yml → podman 命令
生命周期管理 systemd（开机自启、崩溃重启） 手动 up/down
语法 systemd unit 风格，ini 格式 YAML，完全兼容 docker-compose
依赖 零额外依赖（Podman 内置） 需要安装 podman-compose
适用场景 生产环境、长期运行的服务 开发调试、快速原型、Docker 迁移

只读挂载宿主目录（工作方法）

适用场景：迁移 / 备份，容器只读访问宿主数据
目标：容器能读宿主机指定目录，但永远写不进去，宿主数据不被容器改动

方法流程

三步走：加挂载 -> 重载重启 -> 验证读写

关键坑：:ro 只挡写，SELinux 连读一起拦

只加 :ro 时，写被拒（符合预期），但读也报 Permission denied：

原因：宿主目录默认 user_home_t，容器域 container_t 无权读。对比两个挂载源的上下文：

放行读：:ro 改为 :ro,z（z = 共享重标为 container_file_t:s0）：

z or Z：

  • z — 共享标签 container_file_t:s0，可被多个容器读，只读共享场景用它
  • Z — 私有标签 container_file_t:s0:cXX,cYY（MCS 隔离），互不共享的数据卷用它（现有数据挂载即 Z）

三个务必

  1. z 会递归重标宿主源目录——只改元数据不改内容，但含 .ssh/.gitconfig 等点文件的目录不要整目录挂，逐项挂子目录更安全
  2. 敏感目录直接不挂——Configs（含点文件软链）这类目录跳过，其余按文件树逐项挂载
  3. 迁移完整性——SQLite 库 data_v4.db 伴随 -wal/-shm 日志，运行中复制会不一致；先 systemctl --user stop astrbot 再整目录拷贝，拷完 start
